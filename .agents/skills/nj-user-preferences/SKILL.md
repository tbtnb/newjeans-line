# 用户的长期规则与反馈

> 时间按 Asia/Shanghai。“来源”列的是实现这条反馈的 commit（在 `git log` 里可查理由）。带引号的是用户原话。

## A. 原始硬需求（项目开始时定的，一直有效）
| 规则 | 原因 / 备注 |
|---|---|
| 手机竖屏、手机横屏、电脑都能玩 | 用户主要在 iPhone 上玩 |
| 存档可导入导出，旧存档保持兼容 | 新字段要有默认值（例：`settings.skin` 默认 classic，旧存档不变，429e679） |
| 完整音频：不剪、不加速、不循环 | 唯一例外：OMG 用用户自己的谱，在最后一次点击后结束（160.637 s，音乐 1.5 s 淡出，fef26b4 / faa6927） |
| 只要这 16 首、固定顺序（见 nj-project-overview） | 不加伴奏版、不加其它歌 |
| 同一个仓库、同一个 Pages 地址，可回滚 | 所以只用普通 commit，**永不 force-push** |
| 新 UI 和新动效，**没有点击提示** | 原作没有提示；开始画面的手指只表示“点击开始” |
| 验证按类别汇报 | 说清楚哪些验证了、哪些没验证 |

## B. 打点（谱面）
- **每首歌一种一致的点法**，全曲同一套规则（f9a0a4b “one rule set for the whole song”）。
- **人声和歌词是主层**，只有没人声的地方才跟鼓（1f3b671 歌词谱：478 点中 454 在唱出的音节上）。
- 重复的副歌/hook 镜像一致；**节奏逻辑优先于密度**，不要为了 CPM 好看加点。
- 用户亲自在网页打点工具里打点，导出给 agent，agent 只做吸附和微调，**不改点法**（“这是用户自己的谱。只修手的误差”，deliverables/omg-user-import-report.md）。
- OMG 现行谱：用户的 361 点，结束 160.637 s。**不要改这个谱**（交接文档第 5 节）。
- 打点工具：手机单屏 100dvh、不滚动、无点击高亮、不缩放/不选中（9550bd8）。

## C. 路线与路面
- “地图还是往前走的”（2026-10-18）：路线始终朝一个总方向前进（之字形前进），**不盘旋、不回头、不绕圈**。validator 有 FORWARD 硬规则（2961ddc）。
  - 注意：更早的 2026-10-18 反馈“路线不能是简单形状”（levels-design/REFERENCE.md 写了螺旋、U 形弯、回头路）已被“往前走”取代；变化靠交替的阶梯和节奏，不靠回绕。
- **路要宽、容错高**：OMG 路宽 2.6/2.5/2.4（约 2.4–2.6 倍线宽），判定窗口按几何算（f37b6d1）。
- **线头朴素**：没有描边、没有光晕、没有接触圆盘，线头用拖尾同一材质（f37b6d1；之前加过描边/光晕 b0067aa、0b98d13，后被用户否掉）。

## D. 镜头
- 要拉远，要有运镜（9da6416，用户反馈“镜头拉远和运镜”）。同一批反馈还有：音画同步/延迟校准、线头闪烁（c70b3fd）。
- 2026-10-19 原话：“镜头太往下了，这个也要调整一下，线头在屏幕下侧手指点击会挡住屏幕”。
  → 线头固定在离顶部 42%（竖屏）/ 47%（横屏），全曲包括运镜都不能掉下去（60ba8ba）。**以后线头永远不放在屏幕下方**。
- 任何东西都不能挡住线头（视线规则 09935de，起因是约 40 s 处钟楼挡线头）。

## E. 画面
- **华丽（华丽）、元素密集**，但手机要流畅。平淡/稀疏的地图会被否。
  - 预算：高画质 ≤ ~150k 三角形、~45 draws；低画质 ≤ ~50k、~30 draws；高画质撑不住时自动降低档（14f870c）。
- 2026-10-19 原话：“已有的场景也好好打磨，我看现在重复的建模和破碎的建模很多”。
  → **不要重复克隆**（换色板、缩放、部件变体；同款不相邻；每个关键视角克隆对 0–3），**不要破碎模型**（z-fight、重复面、翻面、减面碎片、悬空、穿插）。v8 审计 + 去重轮（2f0d408、e50622e、7b768b0）。
- 风格参照：方案 C 立体童话书 —— 隆起的书页台地 + 花圃、书堆悬崖、卷起的页边、主件靠路、顶部天际线。

## F. 设计先行和模型还原度
- **改地图之前先出设计稿给用户批**：Mac mini 上 Codex 出区域渲染图/设计板，批了再改游戏（omg-design-v3 的 DESIGN.md 开头：“仅设计，不改游戏代码。确认方案后再进入建模/实现”）。
- **每个建筑/大布景都要有细节插图 + 三视图**，模型必须和它一致（IoU 指标）。
- 用户原话（2026-10-19 左右，第一版兔子）：“这个兔子太丑了，和参考图完全不像啊”。
  → 重做 BH1/BH2（尖锐的折纸切面、精确色板）。用户看 BH2 后说“可以的”。**bunny-heart 是还原度标准**，糊成一团（blobby）的模型会被否。
- **分工：Codex 在 Mac mini 上出美术和插图，agent 写代码。**

## G. 流程
- “可以并行做，不用等着”：能并行就并行（多 worker、Mac 和 box 同时跑）。
- 脚本模拟可以当测试，但**必须标明是脚本模拟**，不是真机。
- 要给进度图：每轮发设计稿 vs 游戏的对比图（`deliverables/omg-c-shots/progress-morning.jpg`、`evolution.jpg`），逐区对照。
- “先发到预览链接，我用 iPhone 试玩”：每轮做完先发 `/preview/`，再告诉用户刷新。
- “剩下的也继续补充”：发布之后继续补剩下的缺口，不用等指示。
- “你别继续做了”（2026-10-19）：用户让停就立刻全部停（包括后台任务），报告停在哪个 commit；另一个 AI 可能在接手 `omg-c`，**不要再推 `omg-c`**。
- 2026-10-19：“把你做的关卡……全部做成 skills，然后通过项目的 agents 的 md 索引” + “单独新建一个分支” → 本分支 `level-design-skills`。

## H. 部署
- 只发 gh-pages `/preview/`；根目录和 `/tapper/` 不动；普通 commit；不 force-push；发完核对线上 `preview/build.json` 的 hash（见 nj-deploy-preview）。

## I. 汇报风格
- 用中文，口语、具体：发链接、说刷新、说清楚哪些是模拟、哪些没测到（例：iOS 模拟器卡住没测到时直说“你的手机是第一次真机测试”）。
- 实话实说和设计稿的差距（例：“看上去像平铺的地毯上撒了小物件”），并给出下一轮要做的事。
