# 随每轮工作迭代 skills

这是用户2026-10-19明确要求的项目工作方式，不是独立定时任务，也不授权开展未请求的功能或委派。

## 每轮最低动作
1. 开工读 `nj-user-preferences` 和相关领域skill，核查当前代码/分支；不要将旧实现数字当现状。
2. 记录新反馈的含义、适用范围和取代哪条旧规则。用户纠正“47是百分比”“路宽不用改”等，须改掉旧指令而非堆叠矛盾条目。
3. 修改领域skill：写足以改变后续决策的根因、约束、实现入口和回归条件。普通重构无新经验时仅核对并记录无规则变化，不制造冗余长文。
4. 有新领域才建新skill，并更新根 `AGENTS.md` 索引。共通知识一处维护，历史轮次留在 `nj-lessons-learned/references/`，注明是历史。
5. 同轮提交代码和对应skill，或紧随代码作明确的文档提交。发布后补真实结果：源码/部署版本、测试命令与通过数、尚未验证项；不要把待部署写成已上线。
6. 合并来源分支时，保留原有有效规则，按最新用户意见解决冲突；不让旧技能覆盖新输入、镜头、路线、权限和发布边界。维护文档不扩展为改正式版。

## 写什么 / 不写什么
- 写：可复用的设计理由、约束、资源生命周期、失败模式、测试场景、关键实现路径、可核实commit。
- 不写：口号、未经验证的性能改善百分比、无证据的“完美”、账号凭据、工具私密笔记、把一次局部修复泛化成全项目永恒规则。
- 本轮执行方式由最新用户指令决定，历史并行/Mac工作流不是新授权。
- 分类标识：用户要求 / 当前实现 / 已测试 / 待真机确认 / 历史方案，避免相互混用。

## 校验
- 每个目录含有效YAML `name`/`description`，名称与目录一致；入口说明精确，支持引用可找到。
- 检查AGENTS索引覆盖新增skill；运行可用的skill-validator，再人工检查旧规则冲突与出处。
- 用现实场景自查：早按不能回中；密集副歌不能加下台阶；首次出现模型要预热；回收不能清前方缓存；重开要恢复；无GPU不能说真机通过。
- `level-design-skills` 是文档汇总分支；同步skills时只改该分支的AGENTS/skills，不把游戏代码强行倒回它的旧基线。当前工作分支亦保留同一规范。
